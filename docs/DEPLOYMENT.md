## Application update procedure

For an update, read `/root/oferta-backups/current-release` and inherit that directory's `.release.env`, changing only `OFERTA_RELEASE_TAG`, and link its existing `.env`. This retains infrastructure image pins, the shared network, proxy address, upload path and public web build settings. Check that the merged configuration differs only in application image tags, build context paths, and the already-applied web listener correction. Do not run `prepare-existing-release.py` again: that script is for the original server baseline. Keep the shared Nginx configuration and mounts intact.

Build before stopping any application. Before cutover, record the previous release and image IDs, back up configuration and take a fresh PostgreSQL dump, verify its archive contents, and confirm migration status is current. Recreate only `api` and `web` with `--no-deps --no-build --pull never`, waiting for health. Nginx resolves upstream container addresses when loading configuration, so validate and reload the existing proxy after those containers are healthy. Check API/web readiness through the origin and public hostname, existing image delivery, and the shared sites' HTTP statuses before changing `current-release`.

If API/web readiness or proxy checks fail, restore the previous API/web image configuration with the previous release wrapper and reload Nginx after health returns. Since this update does not change the schema, rollback does not require restoring the database or discarding new customer records. Do not delete volumes or run `compose down`. SMTP authentication repair remains deferred at the operator's request.

## Prepare a release on the existing shared server

```bash
python3 scripts/prepare-existing-release.py --live-dir /opt/OfertaSuksesi
bash scripts/release-compose.sh --progress plain build api web image-service notification-service < /dev/null
```

Preparation reads the live Compose configuration privately, links the existing `.env`, captures the running infrastructure image IDs and network address, and preserves the five public web build arguments. App images receive the release commit as their tag, so building does not replace the previous app image tags. The ignored `.release.env` contains deployment metadata and public URLs, not copied application secrets. The build does not recreate live containers or apply migrations. Use the wrapper for every later Compose command against this release so it consistently selects the existing project, external network, image IDs and absolute upload path. The override uses [`!override`](https://docs.docker.com/reference/compose-file/merge/), supported by the server's Compose 5.1.1.

The preparation script also creates `.nginx.candidate.conf`. It requires Oferta's old blocks to match the known baseline except for certificate paths, retains the live certificate filenames, and appends other sites' blocks unchanged. Cloudflare trust directives are inserted only in Oferta's TLS server blocks, which avoids changing client identity handling for other sites and avoids a new bind mount on the shared proxy. Unexpected configuration edits cause preparation to stop for review. Never replace this candidate with the repository's standalone `nginx.conf` on the shared server.

## Ingress and health

Compose binds database, Redis, search and application ports to loopback; only Nginx publishes external ports. Keep the host firewall consistent with this design. Nginx has a fixed private address and the API trusts only that address. Nginx overwrites forwarded headers and removes the internal-render signature from public requests. Signed server rendering reads avoid a shared browser-rate-limit bucket.

`nginx-cloudflare.conf` trusts `CF-Connecting-IP` only from [Cloudflare IPv4 ranges](https://www.cloudflare.com/ips-v4) and [Cloudflare IPv6 ranges](https://www.cloudflare.com/ips-v6), verified on 19 October 2026. Review these ranges when the proxy configuration changes. Direct clients cannot supply a trusted Cloudflare identity. If using a different proxy/network, update the corresponding trusted addresses together and verify client quotas with two clients and spoofed headers.

API `/api/v1/health` reports process liveness. `/api/v1/ready` probes PostgreSQL, Redis and search with bounded waits: database/Redis failure returns 503; search failure reports degraded service. Web `/api/ready` checks API readiness. Notification `/ready` checks database access, recent worker polling and SMTP connectivity; missing or unavailable SMTP reports degradation. Monitor the JSON status, not just HTTP 200, to detect optional dependency degradation.

To verify web container startup locally, run `docker build --target web --tag oferta-test-web:local .` followed by `pnpm test:container-web`. Set `OFERTA_TEST_WEB_IMAGE` to test another locally built image. The check removes its disposable containers and internal network afterward and does not use the application's `.env`. GitHub checks run it against a fresh Docker build as well as the existing application suites.

## Worker and storage behavior

Search jobs poll every five seconds and re-read current publication state before indexing. Public search results also re-read the database, preventing stale indexed content from being exposed. Expiry, reminder and temporary-suspension reconciliation runs each minute; full search repair runs hourly. Meilisearch totals remain estimates while indexing catches up.

Email/search/media jobs use database claims with five-minute leases, exponential retry and an eight-attempt limit. Completed email event IDs suppress replay and SMTP Message-ID stays stable. Ordinary SMTP cannot guarantee exactly-once delivery if the process dies after the provider accepts a message but before the database records success; monitor this narrow crash window instead of treating Message-ID as a provider idempotency guarantee. Failed deliveries can be inspected and retried in admin operations. Password-reset outbox payloads are encrypted and redacted after completion; the operations API never returns payloads.

New uploads have an ownership registry and one-use permits. Unattached uploads and detached registered files become eligible for cleanup after 24 hours; each job checks current listing/company/ad references and deletes only its authorized stored keys. Historical uploads without registry records are retained. Do not infer ownership from folder names or run a blanket filesystem delete; backfill only from verified legacy asset references if later reclamation is needed. Keep the upload volume persistent across image-service releases.

Current promotion activation is an audited administrative grant with an expiry; customer promotion flags cannot activate it. Payment history displays actual retained payments. There is no online checkout or payment-provider webhook in this release. Advertisements support uploaded image banners only; script/embed formats are rejected and hidden from creation controls. Saved-search matching/email delivery is not advertised as an implemented feature.
